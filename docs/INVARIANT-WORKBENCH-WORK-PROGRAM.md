## Fixed six-workstream denominator

### 1. Contract foundation — built as a local candidate

- Separate workbench `operations` from `realizer_capabilities`.
- Closed capability dictionary and registry schema.
- `DECLARED` versus `MEASURED` standing and exact evidence requirements.
- Closed expression language and semantic validator.
- Typed domains, locks, preferred regions, lowering results, refusals, and revision roots.
- NFC and no-floating-point semantic-root policy with canonicalization vectors.
- Draft 2020-12 example validation plus semantic tests.

Exit evidence: contract/registry checks, schema tests, and the RSC review disposition.

### 2. Obligation Ledger — built as a local candidate

- Enumerate nine assembly requirements from the exact contract.
- Preserve requirement, implementation, proof, scenario, execution, Zucchini,
  counterexample, assumption, and external-gate evidence as distinct classes.
- Record proof at subject scope unless an explicit requirement-to-VC map exists.
- Require explicit, standing-preserving MIW/Zucchini binding records.
- Show unbound Zucchini requirements and open environmental assumptions.
- Compare two rooted workspaces without inferring semantic equivalence.

Exit evidence: deterministic workspace root; binding and non-promotion regressions.

### 3. Invariant Workbench — built through the requested boundary

The CLI and Mosaic Obligation Board can:

- validate an exact dossier and construct the ledger;
- select a requirement and evidence lane;
- create an in-memory or exported proposed Zucchini binding;
- lower a selection to proof recheck, BDD rerun, Zucchini review, dossier
  verification, or conformance-witness plans;
- produce typed refusals for missing evidence;
- explain status and assumptions;
- compare revisions;
- run opted-in local proof/BDD/dossier checks and emit rooted receipts.

The UI uses only controls admitted by the pinned Mosaic application profile.
Network, database, compiler, model, custody, admission, and deployment effects remain
withheld from UI actions.

Exit evidence: CLI lifecycle tests, headless interaction tests, Foundry recompilation,
and native Windows acceptance as a separately reported host gate.

#### 3A. Constitutional control surface

- A closed agent-readable operation registry classifies every CLI and Mosaic action
  by capability, effect class, admission, receipt, and claim ceiling.
- The operation compiler preserves independent subject, admissibility, meaning,
  jurisdiction, and receipt commitments; a compiled plan grants no authority.
- The Mosaic Control Surface validates capabilities, compiles a bounded plan,
  derives read-only diagnostics, and runs the semantic headless court.
- Sentinel, Receipt, and Diagnostic remain distinct observability levels.
- Repair/debug output is advisory and cannot edit sources, delete evidence, contact an
  external system, or admit a release.

## Hard nonclaims

The workbench does not prove specifications correct, infer MIW/Zucchini semantic
equivalence, prove arbitrary C++ or database behavior, establish physical truth,
grant authority, admit releases, or make the local “Realization Space Contract” label
a canonical Ableman-corpus term.
