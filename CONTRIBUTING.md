# Contributing to Invariant Workbench

Invariant Workbench treats claims, source, tests, generated evidence, and release
artifacts as distinct evidence classes. A change is not qualified merely because it
looks correct or passes a narrow test.

## Before opening a change

1. Read `README.md`, `PUBLIC-PACKAGE.md`, `docs/HOW-TO-USE.md`, and
   `docs/SELF-CONTRACT.md`.
2. Keep new effects behind explicit operation and capability boundaries.
3. State assumptions and nonclaims. Do not silently promote test, scenario, runtime,
   or review evidence into proof.
4. Add focused regression tests for the behavior being changed.
5. Do not commit credentials, private data, machine-local paths, generated bytecode,
   or predecessor archives.

## Local qualification

Run from a fresh checkout with Python 3.12 or later:

```console
python -I -B ./tools/qualify.py --out ../iw-qualification
python -I -B ./tools/replay_turn4.py --out ../iw-replay
python -I -B ./tools/miw.py self-contract-check --out ../iw-self-contract.json
python -I -B ./tools/miw.py constitutional-test --directory ./evidence/qualification/demo --bindings ./examples/assembly/workbench.bindings.json --out ../iw-ctr.json
```

Use a new output directory for every run. Some optional lanes require the host
dependencies documented in `README.md`; they must report an explicit boundary rather
than silently skip.

## Pull requests

Describe the obligation changed, the evidence produced, the exact commands run, and
all remaining boundaries. Changes to sealed source require a new manifest and release
identity. Do not edit generated qualification records by hand.
